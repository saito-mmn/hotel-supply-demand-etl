# Hotel Supply & Demand ETL v2 修正方針・ロードマップ

## 1. この文書の目的

本書は、旧ポートフォリオとして作成されたホテル需給分析を、ホテル不動産の担保評価・与信管理を支援する、再現可能な宿泊市場マクロモニタリング基盤へ再構築するための方針を定める。

現行実装は Google Colab 上の単一 Notebook を中心としており、Google Drive の絶対パス、環境依存の処理、依存関係の不足、入力仕様の未定義、保存済み成果物との不整合を抱えている。v2 では、Notebook の見た目を整えることではなく、公式統計の取得から検証、蓄積、分析、レポート生成までを再実行できるデータプロダクトにする。

Phase 1は2026-08-10、Phase 2は2026-08-13に実装・実データ検証済みである。Phase 3以降は計画であり、記載された機能が現在すでに実装済みであることを意味しない。

## 2. プロジェクトの再定義

### 2.1 解決する問い

v2 が扱う中心的な問いを次のように定義する。

> ホテル不動産の担保評価において、対象地域の宿泊需要、稼働率、供給量、需要構成はどのように変化しており、市場環境に悪化または回復の兆候があるか。その兆候は、評価前提の確認やどの追加調査につなげるべきか。

2019 年をコロナ禍前の比較基準として用い、単なる最新値の順位ではなく、基準年からの回復、前年・前回公表からの変化、需要と供給の乖離を監視する。

### 2.2 利用目的

本システムは、ホテル担保の価値を自動算定するものではない。担保評価・審査・与信管理の担当者が47都道府県の統計更新を継続監視し、対象ホテルを取り巻くマクロな市場環境、評価前提の妥当性、追加調査が必要な変化を把握するために利用する。

想定利用者は次のとおりである。

- 金融機関の担保評価担当者
- 不動産鑑定・評価担当者
- 融資審査・与信管理担当者
- ホテル向け融資ポートフォリオの管理担当者

分析結果は、新規評価、定期的な評価見直し、融資先のモニタリングにおいて、地域の市場環境を改善・横ばい・悪化の観点から把握し、評価前提の確認事項を抽出するために用いる。都道府県単位の統計から担保価値、融資可否、個別ホテルの収益性を直接判定しない。

市場変化を検知した後は、対象ホテルとその商圏について次の調査へ接続する。

- 市区町村・商圏別の需要と供給
- ADR、RevPAR、価格帯別の競争状況
- 既存客室数と開業・閉館予定
- 宿泊施設タイプ、ブランド、顧客セグメント
- 交通アクセス、観光資源、イベント
- 対象ホテルの売上、GOP、NOI、修繕費、FF&E
- 運営委託・賃貸借・フランチャイズなどの契約条件
- 土地・建物価値、還元利回り、割引率

したがって、v2の成果物は「担保価値の自動評価」ではなく、全国の地合いを確認するダッシュボードと、担保物件所在地の市場推移を確認する都道府県別Market Sheetとする。

### 2.3 ポートフォリオとして示す能力

- 公的統計APIの調査、認証、取得、メタデータ解決
- APIと公式Excelの提供範囲を判断した取得経路の使い分け
- APIレスポンスと形式の異なるExcelの共通スキーマへの正規化
- SQLite を用いたデータモデリングと版管理
- データ品質検証、テスト、再現可能な実行環境
- SQL・Pythonによる指標構築と、限界を明示した分析
- 定期更新可能なパイプライン設計

## 3. v2 のスコープ

### 3.1 対象に含めるもの

- e-Stat APIからの統計表情報、メタ情報、統計データの取得
- `sources.toml`に明示した2019～2025年の公式Excel取得
- 確定値を中心とした都道府県別月次データの正規化
- 取得経路、統計表IDまたはURL、取得条件、取得日時、レスポンス／ファイルハッシュ、公表区分の記録
- 需要データと供給データの分離保存
- SQLite データベースの再生成
- データ品質検証と回帰テスト
- 都道府県別の月次・年次指標
- 都道府県別マーケットシート
- 市場変化の検知結果と市場ウォッチリスト
- 担保評価上の確認事項を含む可視化レポート
- コマンドラインからの一括実行

### 3.2 初期スコープから除外するもの

- 個別ホテル・個別物件の投資判断
- 担保価値、融資可否、LTV、担保掛目の自動算定
- ADR、RevPAR、売上、利益、投資利回りの推計
- 機械学習による需要予測
- 市区町村・商圏・駅勢圏レベルの分析
- 本番用Webアプリケーション
- 初期段階での全年度・全速報値への対応
- 公式ページHTMLからのリンク自動発見
- GitHub Actionsによる定期巡回と自動PR
- 複数サイトを自動切替する汎用フォールバック基盤

### 3.3 自動化範囲の原則

年確定値は更新頻度が低く、対象ファイル数も限定される。MVPでは取得元を`sources.toml`に明示し、手動実行可能な冪等取得処理を採用する。

MVPで実装する取得機能：

- 設定済み公式URLからのHTTP取得
- タイムアウトとHTTPエラー処理
- `.xls` / `.xlsx`のファイル形式検証
- URL、取得日時、ファイルサイズ、SHA-256のmanifest記録
- 同じハッシュのファイルが存在する場合のスキップ
- 不正ファイルをRaw領域へ確定保存しない処理

初期段階では実装しない機能：

- HTML構造に依存したリンク探索
- 新年度ファイルの自動採用
- 高頻度なサイト巡回
- 成果物の自動コミットまたは自動PR

これらは実装できないから除外するのではなく、更新頻度、誤取得リスク、保守コストに対して便益が小さいため後回しにする。

## 4. データ利用方針

### 4.1 公式データソースと取得優先順位

対象統計は観光庁「宿泊旅行統計調査」とし、取得経路は次の優先順位とする。

- e-Stat API: https://www.e-stat.go.jp/api/
- e-Stat「宿泊旅行統計調査」: https://www.e-stat.go.jp/stat-search?layout=normal&page=1&toukei=00601020
- https://www.mlit.go.jp/kankocho/tokei_hakusyo/shukuhakutokei.html

1. e-Statで配布される公式Excel
2. 観光庁ページで配布される公式Excel
3. e-Stat APIは提供範囲の調査と、対象年が値APIで提供される場合に利用

API提供範囲の実測では、2019・2024・2025年の年確定値は統計値APIの対象として確認できなかった。2019～2025年MVPは公式Excelを主経路とする。APIクライアントは統計表・分類コードの調査と、将来の提供状況の再確認に用いる。詳細は`docs/estat-api-audit.md`に記録する。

取得対象は原則として年次確定値とする。最新動向を扱う場合に限り、第2次速報を別系列として利用する。第1次速報、第2次速報、確定値を無条件に混在させない。

### 4.2 e-Stat API利用方針

- アプリケーションIDは `ESTAT_APP_ID` 環境変数から読み込み、リポジトリへ保存しない
- 統計表IDを推測せず、統計表情報とメタ情報を取得して対象系列を特定する
- 統計表ID、分類コード、選択条件、取得日時、レスポンス形式を記録する
- APIのページング、取得件数制限、タイムアウト、リトライを扱う
- APIレスポンスのRawデータをキャッシュし、同一リクエストを不要に繰り返さない
- 通常テストは保存したfixtureで行い、実APIへの接続を必須にしない
- APIの表改訂、分類コード変更、提供終了を検知して黙って空データをロードしない
- API取得値を公式Excelの標本値と照合し、系列・単位・分類選択が正しいことを確認する

### 4.3 公表区分の優先順位

同じ対象年月に複数の公表区分が存在する場合は、次の優先順位で分析用データを選択する。

1. 確定値
2. 第2次速報
3. 第1次速報

速報値を確定値で物理的に上書きせず、すべての版と出典を保持する。分析用ビューで優先順位を解決する。

### 4.4 制度・定義変更への対応

時系列比較では、少なくとも次の変更をメタデータとして管理し、README とレポートに注記する。

- 2010 年4～6月調査から、従業者数9人以下の宿泊施設が調査対象に追加されたこと
- 公式サイトで訂正値・差し替えファイルが公表されること
- 2026 年1月調査分から、層化変数が従業者数から客室数へ変更されたこと

制度変更をまたぐ数値を単純比較できるとは限らないため、検証警告と分析上の注記を設ける。

### 4.5 Raw データの扱い

- APIレスポンスとダウンロードしたExcelは加工せず `data/raw/` に保存する
- APIは統計表ID、分類条件、取得日時、対象期間、公表区分をmanifestに記録する
- ExcelはURL、ファイル名、取得日時、SHA-256、対象期間、公表区分をmanifestに記録する
- 同名ファイルの差し替えはハッシュ差分で検知する
- Raw データは原則として Git 管理せず、再取得可能にする
- 再配布条件を確認し、公開可否が不明な原本はリポジトリへコミットしない

## 6. SQLite 設計方針

SQLite はe-Stat APIや公式Excelの代替ではなく、両経路から取得した正規化済みデータ、出典、版、品質検査結果を一貫して管理する分析用ストアとして利用する。

### 6.1 主要テーブル

#### `source_records`

APIレスポンスと公式ファイルの来歴を共通管理する。

- source type（`estat_api` / `estat_excel` / `mlit_excel`）
- 統計表IDまたはsource URL
- API分類条件または公式ファイル名
- 公表区分
- 対象期間
- 公表日・取得日時
- RawレスポンスまたはファイルのSHA-256
- normalizer / parser version
- local path

#### `prefectures`

JIS 都道府県コードと正式名称を保持する47件のマスターとする。

#### `monthly_demand_statistics`

都道府県・年月・公表区分ごとの需要統計を保持する。

- 延べ宿泊者数
- 日本人延べ宿泊者数
- 外国人延べ宿泊者数
- 客室稼働率
- source record ID

#### `monthly_supply_statistics`

都道府県・年月・公表区分ごとの供給統計を保持する。

- 施設数
- 客室数など、公式表から安定して取得可能な供給項目
- source record ID

需要と供給を別テーブルにすることで、異なる出典、更新時期、欠損範囲を保持する。

#### `data_quality_results`

取得レコードまたは実行単位の検査名、合否、観測値、メッセージ、実行日時を保持する。

### 6.2 指標の保存方針

入力値から再計算できる指標は、原則としてファクトテーブルに重複保存せず、SQL view または分析モジュールで算出する。

- インバウンド比率
- 2019 年比の需要・稼働率指数
- 需要成長率・供給成長率
- 需要成長と供給成長の差
- 月次変動係数
- 季節集中度
- 市場変化の検知フラグと担保評価向け市場状態分類

指標をマテリアライズする場合は、指標バージョンと生成日時を持たせる。

### 6.3 更新の安全性

- `PRAGMA foreign_keys = ON` を有効にする
- staging table へ投入してから検証する
- 検証成功後に1トランザクションで本テーブルへ反映する
- 再実行しても重複しない idempotent な upsert とする
- 失敗時は既存の正常なDBを保持する
- DB本体は再生成可能にし、原則としてGit管理しない

## 7. データ品質基準

少なくとも次の検証を自動化する。

### 7.1 構造検証

- 必須シートまたは表が存在する
- 必須項目を特定できる
- 都道府県コードが1～47の範囲にある
- 月が1～12の範囲にある
- 都道府県×年月×公表区分のキーが一意である
- 期待する対象期間と実データ期間が一致する

### 7.2 値検証

- 宿泊者数、施設数、客室数が負でない
- 稼働率が0～100の範囲にある
- 外国人宿泊者数が延べ宿泊者数を不自然に上回らない
- 47都道府県の欠落・重複を検知する
- 欠損をゼロへ暗黙変換しない
- 前回公表値からの大幅変化を警告する

### 7.3 来歴検証

- すべての統計行が `source_record_id` を持つ
- APIレスポンスまたはファイルのハッシュが記録されている
- normalizer / parser version が記録されている
- 同名ファイルの差し替えを検知できる

検証エラー時に処理を黙って継続せず、終了コードを非ゼロにして成果物の公開を停止する。

## 8. 分析設計方針

### 8.1 分析する観点

1. 需要回復・成長
   - 延べ宿泊者数
   - 客室稼働率
   - 2019 年比
   - 国内客・外国人客別の寄与
2. 需要と供給のバランス
   - 需要成長率
   - 施設数または客室数の変化率
   - 需要成長率と供給成長率の差
3. 需要の安定性
   - 分析対象期間を明示した月次変動係数
   - 季節集中度
   - 年途中データの除外または明示
4. 需要構成
   - 年間合計から計算したインバウンド比率
   - 国内需要とインバウンド需要のバランス

各観点は、少なくとも次の3つの比較軸で評価する。

- コロナ禍前基準：2019年との比較
- 経年変化：前年の確定値との比較
- 更新差分：前回取得・前回公表からの変化

比較可能な確定値が12か月分揃わない年は年間判定に混ぜず、速報モニタリングとして明確に分離する。

### 8.2 市場ウォッチリストの検知条件

初期版では、根拠の弱い固定幅を避け、次の方向条件を追加調査トリガーとする。

- 直近3か月すべてで需要YoYが負
- 需要LTM YoYが負
- 直近3か月すべてで稼働率前年差が負
- 施設数LTM YoYが正で、稼働率LTM前年差が負

成長・回復についても、需要先行型成長、供給追随型成長、インバウンド主導、コロナ前水準超過をシグナルとして保持する。数値の大きさは全国47都道府県内のpercentileと四分位区分を併記する。検知フラグは担保価値の上昇・下落や融資上の安全・危険を示さず、評価前提または個別ホテル実績を追加確認すべき方向変化を表す。

### 8.3 担保評価向け市場状態分類

単一の総合点だけで順位付けせず、観測事実に基づく類型を基本とする。

- 需要減速・中期縮小
- 足元需要減速・中期縮小・足元稼働悪化
- 供給増加警戒
- 需要先行型成長・供給追随型成長
- インバウンド主導・需要拡大型
- コロナ前水準超過
- 方向感混在・横ばい
- データ不足・比較不能

警戒方向を成長方向より優先表示するが、全シグナルを別項目に保持する。

### 8.4 都道府県別マーケットシート

全都道府県について、少なくとも次の項目を出力する。

- 基準日と利用した公表区分
- 延べ宿泊者数、客室稼働率、供給量の水準と推移
- 2019年同月終了LTM比、LTM YoY、直近3か月YoY、全国相対位置
- 国内客・外国人客の構成
- 月次変動と季節性
- 市場状態分類と根拠値

### 8.5 市場ウォッチリストの出力形式

変化を検知した地域について、次の項目を出力する。

- 対象都道府県と検知日時
- 検知された変化と比較期間
- 根拠となる指標値
- データ品質・比較可能性に関する注意
- 考えられる解釈または仮説
- 担保評価上の確認事項
- 対象ホテルまたは商圏について追加取得すべきデータ
- 評価担当者が行う次の調査アクション

検知されなかった地域も分析母集団から削除せず、検知条件と判定結果を再現できるようにする。

### 8.6 担保評価への利用上の制約

本分析は地域のマクロ環境を把握する補助資料であり、対象ホテルの収益力や担保価値を示すものではない。分析から直接確認できない「供給過多」「担保価値下落」「キャッシュフローの安定性」などを断定しない。出力は次の形式に分ける。

- 観測事実
- 解釈・仮説
- 追加確認が必要なデータ
- 次の調査アクション

## 9. 構造変更と分析ロジック変更の分離

v2では、構造のリファクタリングと分析ロジックの変更を同じ差分に混在させない。

### 9.1 構造リファクタリング

現行ロジックを可能な限り維持しながら、次を行う。

- パス・Colab依存の除去
- 関数・モジュール・CLIへの分割
- SQLiteへの格納
- スキーマ検証とテストの追加
- Notebookを表示・探索用途へ縮小

完了条件は、同じ入力に対する主要な既存指標が、許容誤差内で一致することである。

### 9.2 分析ロジックの改訂

構造移行後、別フェーズで次を検討する。

- 需給指標の分母を施設数とするか客室数とするか
- 全国値は都道府県集計で作らず、観光庁Excel第8表の公式全国客室稼働率を採用する
- 変動係数の対象期間
- 2019年単年基準と2017～2019年平均基準の比較
- 月次比率の単純平均を廃止し、年間合計比率を使うこと
- 年途中データと確定年データの分離
- 市場分類の閾値と根拠

各変更は、定義、変更理由、旧結果との差分、解釈への影響を記録する。

## 10. 実行インターフェース

最終的には次のようなCLIを提供する。

```bash
# e-Statまたは観光庁から公式年確定値Excelを取得
hotel-etl fetch --release final

# Raw APIレスポンス／Excelを正規化してDBへロード
hotel-etl build-db --release final

# 品質検証のみ実行
hotel-etl validate

# 指定年の市場変化を分析し、マーケットシートとウォッチリストを生成
hotel-etl monitor --year 2025 --base-year 2019

# 取得からレポート生成まで一括実行
hotel-etl pipeline --release final --year 2025 --base-year 2019
```

ネットワークを使わず、既存Rawファイルから再構築するモードも用意する。
