# Hotel Supply & Demand ETL v2 ロードマップ

## 1. この文書の位置づけ

本書は、ホテル不動産の担保評価・与信管理で利用する宿泊市場モニタリング基盤について、現在の実装状況と、ポートフォリオ公開・継続更新までの工程を定める。

旧ロードマップは、Google Colab中心の旧プロジェクトから都道府県ETLを構築する段階の計画だった。その後、市区町村第2次速報の月次ETL、SQLite、静的HTMLレポートまで実装範囲が拡大したため、旧計画への追記ではなく、2026年8月時点の現在地を起点とするロードマップへ全面改訂した。旧文書はGit履歴から参照できる。

本書では、次の3種類を区別する。

- **実装済み・レビュー前**：コードと実データ実行は存在するが、設計・分析結果のレビューが完了していない
- **次工程**：ポートフォリオ公開前に必須とする作業
- **Optional**：MVP公開後、運用上の必要性が確認された場合に追加する作業

## 2. プロジェクトの目的

### 2.1 解決する業務課題

ホテル担保評価では、個別物件の収益だけでなく、物件所在地の宿泊需要、客室稼働率、インバウンド構成、施設数、季節性を確認する。特に市区町村値は、月ごとの第2次速報Excelに含まれる複数の参考表を横断し、掲載自治体・非表章値・客室規模区分を考慮して集計する必要がある。

本プロジェクトは、担当者が公式Excelを毎回手作業で加工する代わりに、次を再現可能にする。

```text
公式統計の検出・取得
  ↓
出典・公表日・ハッシュの記録
  ↓
Excelの検証・正規化
  ↓
データ品質検証
  ↓
SQLite更新
  ↓
全国・都道府県・市区町村レポート生成
  ↓
静的サイト公開
```

### 2.2 本システムが行わないこと

本システムは担保価値、融資可否、LTV、ADR、RevPAR、GOP、NOIを自動算定しない。公的統計による市場確認を一次スクリーニングとして提供し、個別物件・競合・収益・契約条件の追加調査へ接続する。

## 4. 更新頻度とデータ採用方針

| ドメイン | 採用データ | 更新頻度 | 役割 |
|---|---|---:|---|
| 都道府県 | 年確定値 | 年次 | 全国の地合い、都道府県マクロ環境、長期比較 |
| 市区町村 | 第2次速報 | 月次 | 担保物件所在地の足元の需要・稼働率確認 |

都道府県速報の月次更新はMVPに含めない。市区町村は足元のローカル市場を確認するため速報を月次更新し、都道府県は確定値で長期的な市場環境を年次更新する。公表区分と利用目的を分離し、速報値と確定値を同じ系列として無条件に混在させない。

2019年を開始年とする。2015～2018年への拡張は、2019年以降だけでは回答できない具体的な分析要件が生じた場合のOptionalとする。

## 8. Phase 2：コード・データ品質レビュー

### 目的

### 8.1 市区町村レビュー

- 5つの参考表を自治体・客室区分で結合する方法
- 指標別に掲載自治体が異なる場合の和集合とNULL処理

- 公式表の小数利用客室数を保持する理由
- 100%超稼働率を補正しない理由と表示上の警告

- 冪等ロード、対象月置換、トランザクション

### 8.3 統合レビュー

- 都道府県推計値と市区町村実数を別ファクトとして保持しているか

- source ID、URL、公表日、取得日時、SHA-256まで追跡できるか
- CLIの責務と失敗時の終了コード
- DB更新失敗時に既存の正常データを保持できるか
- 型ヒント、例外階層、モジュール境界
- fixture、回帰テスト、実データ検証の役割分担

### 8.4 要検討：公式ファイルの訂正・差し替え履歴

観光庁は年確定値の初回公表後に数値や配布Excelを訂正することがある。たとえば2024年確定値は2025年6月27日に初回公表され、2025年8月26日に訂正が公表されている。現在の`sources.toml`の`published_on`は基本的に初回公表日を記録しているため、採用中のExcelが訂正版である場合、その更新時点を単独では表現できない。

Phase 2で次を決定する。

- `published_on`を初回公表日として固定するか、現在採用中ファイルの公表・更新日とするか
- 初回公表日と訂正日を`first_published_on`、`revised_on`などの別項目で保持するか
- レポートの「データ公表日」に初回公表日、最終訂正日、または両方のどれを表示するか
- 同一URLの内容差し替えと、新URLへの差し替えをどのように検知するか
- 旧ハッシュ・旧URL・訂正理由をmanifestまたは別の履歴として残すか

少なくとも、ハッシュ変更を検知した際に既存の来歴を黙って上書きせず、訂正版の採用前に対象年・公表区分・Excel形式・主要値を再検証できる設計とする。

## 10. Phase 4：GitHub Pagesによる静的デモサイト公開

現在のレポートは静的HTMLで完結するため、MVPではWebアプリ、常駐APIサーバー、公開DBを構築しない。評価者がREADMEからすぐに完成物を操作できるLive Demoを提供することを目的として、生成済みHTML、CSS、JavaScriptをGitHub Pagesへ公開する。

GitHub Pages自体を本プロジェクトの静的ホスティング先とする。Cloudflare Pages、Vercel、Netlify、S3 + CloudFrontなどを重ねて導入しない。Pull Request単位のPreview環境が必要になった場合に限り、Cloudflare PagesまたはVercelを再検討する。

```text
SQLite（非公開）
  ↓ report generator
静的HTML一式
  ↓ GitHub Pagesへdeploy
Live Demo
```

### Phase 4の公開方法

- 最初は`reports/latest/`の生成済みHTMLを使い、手動デプロイの手順と公開対象を固定する
- README上部からLive Demoへ直接到達できるリンクを設置する
- 全国レポートから都道府県・市区町村一覧、各Market Sheetまで相対リンクで遷移できることを確認する
- GitHubリポジトリはソースコードとレビュー用生成物、GitHub Pagesは操作可能な成果物という役割に分ける
- Phase 6でCIからの自動生成・自動デプロイへ移行するまでは、`reports/latest/`をGit管理する

### 公開しないもの

- Raw Excel
- SQLite
- `.env`、e-StatアプリケーションID、認証情報
- ローカルパスを含むmanifest
- レビュー用一時ファイル

### 作業・完了条件

- GitHub Pagesの公開元と手動デプロイ方法を決定・文書化する
- 相対リンク、404、キャッシュ、文字コードを確認する
- 出典、対象年・最新掲載月、データ公表日、必要な指標定義を表示する
- 秘密情報・個人パス・不要な巨大ファイルを再スキャンする
- 公開URLから全国・都道府県・市区町村へ到達できる
- ローカル生成物と公開HTMLの件数・メタデータが一致する
- 手動デプロイを再現できる
- READMEの目立つ位置にLive Demoへのリンクがある

### 実装状況（2026-08-17）

- `.github/workflows/pages.yml`に、`workflow_dispatch`による手動デプロイを実装した
- `scripts/prepare_pages.py`に、公開ファイルの選別、Market Sheet件数照合、内部リンク検証、公開ルート逸脱・機密情報・シンボリックリンクの検査を実装した

- README上部にLive Demoリンクを追加し、`docs/deployment.md`に初回設定、手動実行、ローカル検証を記載した
- Phase 4ではレポート生成を自動化せず、レビュー済みの`reports/latest/`だけを公開する。定期生成・自動デプロイはPhase 6へ分離する

GitHub上での初回Pages設定、デフォルトブランチへの反映、workflow実行、公開URLの実機確認まで完了した。2026年8月18日にPhase 4のざっくりしたコードレビューと表示確認を完了し、詳細レビューはPhase 6の自動デプロイ着手前に再確認する。

## 11. Phase 5：更新パイプライン

### 11.1 市区町村月次更新

```text
第2次速報の最新公表月を検出
  ↓
既存manifestとの差分確認
  ↓
原Excel取得・形式・ハッシュ検証

5参考表のparse・品質検証
  ↓

  ↓

```

追加実装：

- 第1次速報や閲覧用Excelを誤採用しない
- 既存ファイル差し替えをハッシュ変更で検知する
- e-Statリンク欠落時に自動推測せず停止する
- 観光庁例外ソースは明示設定または承認付きで採用する
- parser・品質検証失敗時は既存DBと公開HTMLを維持する

### 11.2 都道府県年次更新

- 新しい年確定値を検出する
- 過年度確定値の訂正公表、URL変更、同一URLのハッシュ変更も検出する
- 初回公表日と訂正日をPhase 2で決定した定義に従って記録する
- 訂正版を採用する場合は旧URL・旧ハッシュ・採用日時を履歴として保持する
- 確定値、対象年、12か月、47都道府県を検証する
- SQLiteの都道府県ファクトを再生成する
- 既存市区町村テーブルを保持する
- 全国・都道府県HTMLを再生成する

### 完了条件

- 新規データがある場合だけ更新する
- 新規データなしは正常終了し、DB・HTMLを変更しない
- 取得、検証、DB反映、HTML生成を1コマンドで実行できる
- 途中失敗で正常な公開レポートを壊さない
- 手動再実行と特定年月の再処理が可能
- 過年度訂正を検知・再検証し、変更前後の来歴を追跡できる

### 実装状況（2026-08-18）

- `check-updates`で、観光庁の年確定値とe-Statの月次第2次速報の公式一覧ページを読み、設定との差分だけを確認できる
- e-Statでは第2次速報・原Excel（`fileKind=0`）だけを採用し、第1次速報と閲覧用Excelを除外する
- `update`で両ドメイン、`--domain`で片方だけを更新できる
- `ETag`・`Last-Modified`の条件付き確認とSHA-256比較により、同一URLの差し替えを検知する
- URL・source ID・ハッシュ変更前の来歴をmanifestの`revisions`へ保持する
- 市区町村は変更期間だけを一時DBへトランザクション反映し、都道府県は全確定値を一時DBへ再生成する
- DB、HTML、ソース設定は全検証成功後に切り替え、切替失敗時は旧成果物を復元する
- 新規データなしは`updated: false`で正常終了し、DBとHTMLを変更しない
- `--periods`・`--years`で特定期間を手動再処理できる
- 観光庁例外ソースの競合と、新規年確定値の公表日不明は自動推測せず、承認・設定要求として報告する

実公式ページに対する`check-updates`の動作確認まで完了した。実ファイルを取得する`update`の本番実行と、更新発生時の実データ差分レビューは未実施である。

## 12. Phase 6：CI・定期実行・自動デプロイ

### CI

- Pull Requestおよび通常のpushでは外部公式サイトへアクセスせず、固定fixtureを使って検証する
- クリーン環境へのインストール
- unit test・fixture test
- formatter・lint・型検査
- SQLiteスキーマ・件数検査
- HTML生成数・リンク切れ検査
- 秘密情報・個人パス検査

### 定期実行

- 市区町村：月次第2次速報の公表サイクルに合わせて確認
- 都道府県：年確定値の公表サイクルに合わせて確認
- 公表日が変動するため、安全な確認期間を設ける
- 新規データなしは失敗としない
- 失敗時はログと通知を残す

### GitHub Pages自動デプロイ

通常のコード検証と公式データ更新を別ワークフローに分離する。

```text
Pull Request / push
  ↓
test・lint・固定fixtureによるレポート生成・HTML検証

定期実行 / 手動実行
  ↓
公式データ取得・品質検証・SQLite更新
  ↓
レポート生成・HTML検証
  ↓ 成功時のみ
GitHub Pagesへdeploy
```

外部サイトの一時障害やURL変更によって通常のPull Request検証や正常な公開サイトを壊さない。データ更新に失敗した場合は、前回成功時のGitHub Pagesを維持する。

### デプロイ品質ゲート

自動取得したファイルを無条件に公開しない。公式ホスト・公表区分・対象年月、XLSX・ハッシュ、parser、品質検証、HTML件数・リンク、既存データからの件数変化を確認し、成功時だけ新DBとHTMLを確定する。

### 完了条件

- CIがPull Requestまたはpushで再現可能に動く
- 定期実行と手動実行の両方を利用できる
- 成功時だけ静的サイトが更新される
- 失敗時に前回の正常サイトが維持される
- GitHub ActionsからGitHub Pagesへの生成・検証・デプロイが再現可能である
- 自動デプロイ安定後に、`reports/latest/`をmainブランチで管理し続けるか再判断している

### 実装状況（2026-08-18）

- `.github/workflows/ci.yml`に、Pull Request・`main`へのpushを対象とする外部公式サイト非依存のCIを実装した
- クリーン環境へのinstall、Ruff、更新系モジュールを対象とするmypy、unit・fixture test、SQLiteを含む統合テスト、追跡ファイル検査、HTML件数・リンク検証を品質ゲートにした
- 既存parser・analysis・report・CLIには型エラーが残るため、mypyの対象はPhase 5・6で追加した更新系から開始し、全`src`への拡張はコードレビュー後の技術的負債として残す
- `.github/workflows/update-and-deploy.yml`に、市区町村の週次確認、都道府県の6～8月確認期間、ドメイン指定の手動実行を実装した
- 前回成功時のRaw Excel、manifest、SQLite、採用ソース設定、生成レポートをActions Cacheから復元し、差分更新に利用する
- `approval_required`・`configuration_required`、ETL・品質検証・HTML検証の失敗時はdeployせず、前回のPagesを維持する
- 新規データなしは正常終了し、通常は再デプロイしない。手動時だけ既存生成物の強制再公開を選べる
- 更新結果、採用設定、manifestを監査artifactとして30日間保持する

Phase 6のローカル実装まで完了した。Phase 5・6のコードレビュー、GitHub Actions上の初回実行、定期実行の安定性確認は未実施である。したがって、`reports/latest/`をmainブランチで管理し続けるかの判断は、複数回の更新成功を確認するまで保留する。

## 16. 工程管理上の原則

- 分析ロジック変更と構造リファクタリングを同じ変更単位にしない
- 公式値を暗黙に補完・丸め・上限補正しない
- 例外を見つけた場合はコード、テスト、文書へ固定する
- 自動化は失敗時に既存の正常なDB・レポートを壊さない
- 生成物の多さを完成度とみなさず、業務目的に必要な表示へ絞る
- 公開前に秘密情報、個人パス、Rawデータ、巨大ファイルを確認する
- 本人が説明できない抽象化や過剰設計を追加しない
